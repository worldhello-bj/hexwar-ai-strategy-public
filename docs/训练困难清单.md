## 1. 训练入口缺陷（已定位并修复）

### D1 —— `eval` 不支持神经（PPO）检查点

**症状**

```powershell
cd train
py -3.13 run_train.py ppo  --config configs/ppo_realmap.json
py -3.13 run_train.py eval --config configs/eval_realmap.json --checkpoint analysis/realmap/ppo160.json
# → policy_eval.py: error: unsupported checkpoint     （退出码 2）
```

**根因**：`run_train.py` 把 `eval` **一律**转发给 `env/policy_eval.py`，而它只认 MC 表检查点
（`env/selfplay.py::SelfPlayTrainer.load` 第 171 行 `raise ValueError("unsupported checkpoint")`）。
神经检查点由 `env/neural_train.py::NeuralTrainer.load` 加载，两个加载器**互不兼容**。
⇒ `train/README.md` 与 `skill/hexwar-training/SKILL.md` 里写的 `ppo → eval` 流程**必然失败**。
（历史提交 `791600d` 修过一次，随即被 `5a5bd17` 整个 revert。）

**修法**

| 文件 | 改动 |
|---|---|
| `env/neural_train.py` | 新增 `--eval-only`：只载入检查点评测，**不训练、不改检查点**，与训练收尾同一个 `evaluate()` |
| `train/run_train.py` | 新增 `checkpoint_kind()`，按检查点 `algorithm` 字段分流（`first_visit_terminal_mc` → MC 评测器；`neural_terminal_*` → `--eval-only`；不认识 → **报错不猜**）；神经分支允许命令行 `--report/--snapshot/--seeds` 覆盖配置 |

**验证**：`check` / `rules` / `ppo→eval` 端到端 / MC 检查点回归 / 坏输入报错 —— 全部通过；`pytest tests` **213 passed, 1 skipped**。

### D2 —— `run_train.py check` 永远误报

**症状**：`train/` 明明已生成（`MANIFEST.json` 在），却报

```
train/ 还没生成过：先跑 py -3.13 tools\build_train_env.py        （退出码 1）
```

**根因**：它调用的是 `train/tools/build_train_env.py`（**副本**），而该脚本按自身位置推导
`ROOT = dirname(dirname(__file__))` ⇒ `ROOT` 算成 `train/`、`TRAIN` 算成 `train/train`（不存在）。

**修法**：改调**主仓库根**的 `tools/build_train_env.py`；外侧无主仓库（独立副本布局）时说明后返回 0。

## 2. 训练「学不动」的原因（核心困难）

### 2.1 T1/T2 —— 奖励口径本身：绝对分 + 按席位的常数

**代码事实**

| 环节 | 现值 | 位置 |
|---|---|---|
| 奖励信号 | 学习者的**本方终局原始分** `own_score`（`verified` 口径） | `env/neural_train.py` `_rollout` → `pending.append((trajectory, record["own_score"]))` |
| 时间结构 | **纯终局**，中途恒 0，$\gamma = 1$，无折扣 | `episode_api` 的 terminal-only 契约（非终局出现非零奖励会 `raise`） |
| 优势 | $A = r - \text{offset} - V(s)$，`V` 为**观测特征的线性价值头** | `neural_policy.update_batch` / `_update_ppo` |
| 基线 | `baseline_offset ∈ {none(默认), prior_batch_mean}` | `neural_policy.__init__` |
| 归一化 | 优势**不归一化**、回报不缩放、**无熵奖励** | `_loss_gradients` |
| 席位 | 按局序号轮换（`SIDES[index % 2]`），**同一 batch 混两个席位** | `neural_train.train` |

**问题**

1. 蓝方轨迹的回报恒在 **234–414**，红方恒在 **354–588**。批次里两种量级混在一起，
   线性价值头得先花容量学「我是哪一方」，而 Adam 看到的是移动的目标。
2. `r = 234` 与 `r = 354` 不含任何技能信息，是**场景常数** ⇒ 纯方差。
3. 因为判据是**净胜分**而奖励是**本方分**，口径不一致（虽然同一局内二者只差一个仿射变换，
   但跨局的仿射系数会变——`红总分 + 蓝总分 = 588 + 已被占据的点分`）。

**可选方案**（详见讨论记录）

| 方案 | 形式 | 优点 | 代价 |
|---|---|---|---|
| **A. 相对开局的本方增量** | $R = \text{own}_{\text{终}} - \text{own}_{\text{开}}$ | 改动最小；「不动 = 0」；蓝抢两点 = +130 | 非零和 |
| **B. 相对开局的净胜分** ⭐ | $R = (\text{own}-\text{enemy})_{\text{终}} - (\text{own}-\text{enemy})_{\text{开}}$ | **与判据完全一致**；零和；分辨率 ×2 | 随机对手下方差更大 |
| **C. 稠密化（望远镜）** ⭐ | $r_t = \Phi(s_{t+1}) - \Phi(s_t)$，$\Phi = \Delta$净胜分 | $\gamma=1$ 时 $\sum r_t$ **恒等于** B ⇒ **可证明不改变最优策略**；抢点变成局部 +80 | 要改 `update_batch` 入参 ⇒ `pending` schema 变更、需重训 |
| **D. 胜负 ±1** | $R = \operatorname{sign}(\text{own}-\text{enemy})$ | 最贴近「赢」 | 丢掉幅度；开局 −120 使红蓝近乎必然输赢 ⇒ 退化。**不推荐单用** |

### 2.2 T3 —— 优势会被价值头「吃掉」

$A = r - V(s)$。`V` 是线性头、学得很快；当策略接近「不动」时，$r$ 几乎是常数 ⇒ $V \to r$ ⇒
$A \to 0$ ⇒ 梯度 $\to 0$ ⇒ **停滞**。这是「纯终局 + 可学价值头 + 低方差回报」的典型失效模式，
与 `真实地图训练.md` §4.2.3 记录的「初始策略与训练后策略 8 局完全一致」吻合。
**最便宜的缓解是批内优势归一化**（现在完全没有）。

### 2.3 T4 —— `prior_batch_mean` 在这个场景里是陷阱

它维护的是**跨全部轨迹**的滚动均值；蓝起手 234、红 354，减掉一个混合均值后仍留 **±60 残差**。
⇒ 不能用它替代「按席位扣开局分」。若采用方案 A/B，这个选项就**不需要了**。

### 2.4 T5/T6 —— 采样效率（我认为这才是主瓶颈）

| 量 | 值 |
|---|---|
| 每决策的候选动作数 | **300–700**（`move_radius` 3–4；半径 4 时实测均 559.7 / 上限 694） |
| 一局双方决策数 | **12–19** |
| 160 局能提供的样本 | ≈ **1600–2200 条决策** |
| 需要「发现」的行为 | 蓝方用 **3–4 个决策**把够得着的两个点占了（+130） |

在 500 路平铺 softmax 上做随机搜索去找一串 3–4 步动作，样本量差着几个数量级。
**建议**：动作头**因子化**（先选单位 → 再选动作类型 → 再选目标/落点），或早期把 `move_radius` 压到 1–2。

### 2.5 T7 —— 对手是均匀随机

两个后果：
1. 它提供不了有意义的对抗压力，学到的策略没有「被惩罚」的机会；
2. 若奖励改用净胜分（方案 B），**对手的分数波动会直接进奖励** ⇒ 方差上升。
   ⇒ 这里有个真实取舍：**要么用方案 A（只看本方）压方差，要么给对手加一个脚本策略**
   （例如「抢本方可及的点 + 打最近敌人」）。

### 2.6 T8 —— 稠密化的改造成本（已评估）

阻点：`episode_api` 的 terminal-only 契约（`neural_train._rollout` 里有一条断言：非终局出现非零
`rewards` 即 `raise ValueError`），以及 `update_batch` 现在只接受**每条轨迹一个标量**、
检查点的 `pending` 存的是 `{"decisions": ..., "return": score}`。
两条路：
- 改契约（要同步改 `tests/test_episode_api.py` 等）；
- 或**不动契约**，在训练器侧对连续两次观测的公开比分做差分（`public_score=True` 已经在观察里
  下发 `own/enemy/diff`）。**后者代价小得多，推荐先走这条。**

## 3. 想定 / 分数结构带来的困难

### 3.1 S1 —— 「席位居优」是错觉，但很容易误导

| | 值 |
|---|---|
| 开局 | BLUE **234** / RED **354**（净胜分 **−120**） |
| 夺控点 | 主要 80 + 次要 50 + 次要 50 = **180**，开局全 `GREEN`（中立） |
| 蓝方「什么都不做」 | −120（输） |
| 蓝方拿下**够得着**的主要+次要B（+130） | 234+130 = 364 vs 354 ⇒ **净胜 +10** |

⇒ **目标其实是决定性的**：抢点值 130 分，刚好覆盖开局 120 分的劣势。
`真实地图训练.md` 里「胜负由席位决定」只在「双方都不动」时成立 ——
它真正的含义是「**不动就必输**」，而不是「努力也没用」。

### 3.2 S2 —— 决策预算 vs 单位数量

每方 18 个单位，而一局每方只有 **6–10 次**决策（一方一次只能指挥一个单位的一个动作）。
⇒ **绝大多数单位整局都不会被指挥到**。这不只是奖励问题，是**动作表示 / 时钟长度**的问题。

### 3.3 S3 —— 夺控点的可达性（实测，含 30 s 夺控判定）

| 点 | 分值 | 蓝方最早 | 红方最早 | 谁先到 |
|---|---|---|---|---|
| 主要 `160066` | 80 | **90 s** | 246 s | 蓝方 |
| 次要A `160073` | 50 | 210 s | **198 s** | 红方（仅早 12 s） |
| 次要B `160060` | 50 | **150 s** | 282 s | 蓝方 |

⇒ 蓝方先拿到 130 分（主要 + 次要B），**第三个点红方只快 12 秒** ——
局面其实是**胶着**的，不是一个已经打完的想定。这对奖励设计是好消息：
「抢点」这条学习目标存在且可达。

### 3.4 S4 —— 净胜分摆幅（用于讨论权重）

| 事件 | 净胜分摆幅 |
|---|---|
| 夺下「主要」 | **80** |
| 夺下「次要」 | 50 |
| 整歼一辆 RED 坦克（score 10 × blood 4 = 40） | **80**（我方歼灭 +40，对方剩余 −40） |
| 整歼一辆 BLUE 坦克（score 10 × blood 3 = 30） | 60 |

⇒ **打掉一辆坦克 ≈ 抢下一个主要点**。若想「任务导向」而不是「消耗战导向」，
就必须显式给夺控加权 —— 而**权重没有规则依据**（见 R2），属设计选择，必须版本化。

### 3.5 兵力分构成（供核对）

- RED 354 = 6×40（坦克/火力支援车）×3 + 3×20（侦察车）+ 3×16（步兵班）+ 3×2（无人机）+ 3×0（巡飞弹）
- BLUE 234 = 6×30（坦克/装甲车）+ 4×9 + 2×6 + 3×2 + 3×0
- 注意 **巡飞弹 `score = 0`** ⇒ 打掉它不给分。

## 4. 规则 / 计分上的未确证项（直接影响奖励正确性）

来源：`docs/未确证裁决表.md`、`docs/规则符合性.md`、`docs/计分规则待确认.md`。

| 编号 | 项 | 现状 | 影响 |

## 5. 数据与工程侧的困难

### E1 —— 数据源只剩公开想定

`snapshot/parsed/` 已空 ⇒ `engine/paths.py::snapshot_dir()` 回退到 `scenario/7527`；
规则门的 `--live`（线上实测裁决逐条对账）**没有样本**，只做引擎侧自检。
⇒ 线上任何新证据都必须重新采集（脚本需 `HEXWAR_USER` / `HEXWAR_PASS` + `HEXWAR_ALLOW_HTTP=1`）。

### E2 —— `train/` 是生成副本

`train/{engine,env,tools,tests,offline,docs,scenario}` 由 `tools/build_train_env.py` 从**仓库根**
同步（逐字节相同），手工维护的只有 `README.md` / `run_train.py` / `configs/` / `skill/`。
⇒ **改了根 `engine/`、`env/` 必须重新同步**，否则 `train/` 在用**旧规则**训练。
有门禁：`py -3.13 run_train.py check`（已随 D2 一起修好）。

### E3 —— 产物不入库

`analysis/`（根与 `train/`）、检查点、报告都在 `.gitignore` 里 ⇒ **基线无法跨机复现**，
CI 也只能跑冒烟而不能比对历史数字。

### E4 —— 配置只能跑一次

`configs/*.json` 把 `checkpoint` / `report` **写死**，而各入口的守卫是「产物存在即拒跑」：
```
selfplay.py: error: output exists; choose new filenames
```
⇒ 文档里的命令在**第二次**执行时必然失败（需先删 `train/analysis/` 下的产物）。
守卫本身是**有意为之**（报告是证据、不许静默覆盖），所以这是个**取舍**而不是纯 bug。

### E5 / E6 —— 文档漂移与自相矛盾

- `engine/scoring.py` 是 `SCORING_VERSION = 6`，但 `计分规则待确认.md` §6 写「`SCORING_VERSION = 4`」，
  `真实地图训练.md` 头部也写 4（同一文件的 §4.2.3 又按 6 讨论）。
- `计分规则待确认.md` 的 **§5.2 / §5.3 各出现两次**，且结论冲突：
  L338/L346 说「载员被歼**已实测**」，L351/L357 说「**尚未直接观测**」。

⇒ 这两条会直接误导阅读者（尤其 E6：同一问题两个相反结论）。

## 6. 优先级与建议下一步

| 优先级 | 事项 | 为什么这个顺序 |
|---|---|---|
| **P0** | 修 E5 / E6（文档自相矛盾与版本漂移） | 成本极低，但会持续误导判断 |
| **P1** | 奖励换成 **方案 B（相对开局净胜分）** + **批内优势归一化** | 改动小、可与现有基线同种子对比；直接对治 T1/T2/T3 |
| **P1** | 小额**熵奖励** | 对治 T5（策略塌到 `wait` 后无梯度） |
| **P2** | 动作空间**因子化**（或早期 `move_radius=1–2`） | T6 是最大瓶颈，但改动面比奖励大 |
| **P2** | **课程**：阶段 1 只放蓝方、目标 = 守住够得着的点；阶段 2 加红方；阶段 3 全量 | 比把 160 局堆到 1600 局有效 |
| **P3** | 稠密化（方案 C），走「训练器侧差分公开比分」不动契约的路线 | 有收益但需 schema 变更与重训 |
| **P3** | 给对手加脚本策略（替代均匀随机） | 决定方案 B 的方差是否可接受 |
| **待外部** | R1 / R2 / R3 向主办方索取 | 拿不到就只能维持「不臆造」 |

### 需要拍板的三件事

1. **奖励口径取 A 还是 B？** —— 更怕**方差**（选 A）还是更想要**与判据对齐**（选 B）。
2. **允不允许中途稠密奖励？** —— 这会决定是否要动 `episode_api` 的 terminal-only 契约。
3. **要不要动动作空间 / 上课程？** —— 我认为收益最大，但改动面最大。
