## 一、为什么以前练不了：枚举里藏着 1500 次整状态深拷贝

`HexwarEnv.legal_actions()` 原本对**每个候选动作**都调用
`_try_actions([a], commit=False)` 做事务校验，而 `_try_actions` 会
`copy.deepcopy` 整个 `Game`。合成场景（320 格 / 6 单位）看不出问题，真实地图上：

```
cProfile（真实地图、半径 6、1549 个候选）
  13.692s  legal_actions
  13.637s    └─ _try_actions            ← 1911 次调用（= 候选数）
  13.076s         └─ copy.deepcopy      ← 7M 次函数调用，占总耗时 95%
```

**瓶颈不是寻路、不是通视，而是"为每个候选复制一次世界"。**

| 机动半径 | 候选数 | 参考口径（逐候选深拷贝） | 快速口径 |
|---|---|---|---|
| 1 | 109 | 0.103 s | **0.019 s**（×5.4） |
| 3 | 469 | 0.512 s | **0.023 s**（×22.1） |
| 6 | 1549 | 1.809 s | **0.042 s**（×43.4） |

快速口径的开销几乎不随半径增长（不再逐候选复制），所以训练可以直接用**半径 6 的完整动作空间**。

## 二、快速口径怎么保证不变错

`legal_actions(deep_validate=False)`（现默认）只对**不需要引擎裁决**的动作类型放宽：

- `READONLY_TYPES = ("move", "wait", "stop", "stop_attack")` → 走只读判定 `_cheap_ok`；
- 其余（`attack` / `area_fire` / `grenade` / `capture` / `load` / `unload` / `hide`）
  **仍走原事务校验**——它们才需要 `game.attack()`、`apply_city_capture()` 之类的真裁决，
  数量也少（真实地图开局 0 个可见敌人 → 0 个射击候选）。

只读判定必须严格对齐事务校验的两处细节，否则会枚举出 `step()` 会拒的动作：

1. **`wait` 故意豁免剩余时间上限**：`_try_actions` 的时间检查只在非 `wait` 分支里，
   超时的等待被**截断**到剩余秒（这正是时钟能正好走到 `max_seconds` 的原因）。
   第一版漏了这条，`tests/test_rollout_invariants.py` 立刻抓到（`legal_actions()` 返回空）。
2. **冲锋单位一个动作只能走 1 格**：`commit_step` 每格累加 200 米，而手册 4.1.1(4)
   满 200 米即转疲劳 → 多格路径的第二格必被拒。BFS 在**未变状态**上逐跳算
   `step_seconds`，看不到这个累积，所以要显式补上。

### 等价性证据（两道）

- **CI 用例** `tests/test_enumeration_equivalence.py`（5 项）：合成场景上逐决策比较两种口径的
  动作集合、枚举只读性（状态 + 随机数流）、抽查候选被 `step()` 接受且机动耗时一致，
  并覆盖冲锋与时钟耗尽两个边界。
- **真实地图差分** `tools/hex_env_diff.py`（可在 `snapshot/parsed` 上本地跑）：

```bash
py -3.13 tools/hex_env_diff.py                                   # 合成 demo，20 决策点
py -3.13 tools/hex_env_diff.py --snapshot snapshot/parsed --radius 3 --steps 12
```

实测两边都是 **0 分歧 / 0 非只读 / 0 被 step 拒 / 0 耗时不一致**：

| 场景 | 决策点 | 每点候选（快速/参考） | 结论 |
|---|---|---|---|
| `samples/demo` r2 | 20 | 66–84 | 等价 ✅ |
| `snapshot/parsed` r3 | 12 | 451–453 | 等价 ✅ |

> ⚠️ 真实地图不会进 CI（`snapshot/` 不入库），所以真实地图一侧靠本地复跑；
> 想复现就按上面第二行命令跑。

## 三、打开「真实地图训练」的开关

训练/评估器原本**硬性拒绝**非合成快照（`snapshot_manifest` 要求
`evaluation_provenance.json` 里 `origin == "original_synthetic"`），这条门禁默认仍然生效。
真实想定必须**显式 opt-in**：

```bash
# 单方跑分（本来就是真实地图为默认快照）
py -3.13 env/run_episode.py --agent greedy-multi --episodes 3 --snapshot snapshot/parsed

# 双边自重博弈（首次访问蒙特卡洛）
py -3.13 -m env.selfplay --snapshot snapshot/parsed --allow-real-map \
  --move-radius 4 --episodes 60 --max-seconds 1200 --max-steps 600 \
  --seed 0 --eval-seeds 1000000 1000001 \
  --checkpoint analysis/realmap/mc60.json --report analysis/realmap/mc60_report.json

# 神经策略（PPO clip）
py -3.13 -m env.neural_train --snapshot snapshot/parsed --allow-real-map \
  --move-radius 3 --episodes 160 --batch-episodes 8 --max-seconds 1200 \
  --update-mode ppo_clip --ppo-clip 0.2 --update-epochs 4 \
  --buckets 4096 --hidden-dim 64 \
  --checkpoint analysis/realmap/ppo160.json --report analysis/realmap/ppo160_report.json
```

新增参数：`--allow-real-map`、`--move-radius`、`--deep-validate`。
`snapshot_manifest(path, allow_real=True)` 会把来源标成 `origin="local_real_map"`，
并**仍然哈希三个被读取的文件**——所以本地运行依旧可复现，且
`--allow-real-map` 不传就一定会报错（不会静默拿真实数据当合成场景）。

产物一律写在 `analysis/`（已 gitignore），真实想定数据与训练产物都不入库。

#### 4.1.2 修复后重跑（`--scoring verified`，2026-10-15 第二轮）

同参数（`--move-radius 4 --episodes 60 --max-seconds 1200 --max-steps 600 --seed 0

| 指标 | 值 |
|---|---|
| 每局步数 | 8 – 33（均 21.9） |

★★ **重要发现：`verified` 口径下"抢点"没有任何分值**。已确证的只有剩余兵力分，
而夺控分是无依据占位（默认被排除）、歼煍分是假设（同样被排除），于是：

- 占一个点对奖励**没有任何影响** ⇒ MC 不再抢点，**60 局里 44 局双方零损失**（比分就是开局值）；
- 剩下能学的只有"消耗战"（把对方兵力打下去）；
- 对比一下旧口径（§4.1.1）：当时每个夺控点值 ±10 分，才是它驱动了 30 种不同比分。

⇒ 结论：**干净的奖励目前是"不完整的奖励"**。要训练"夺控"这类目标，
必须先拿到官方的夺控分口径（见 `docs/计分规则待确认.md` §4A）；
在拿到之前，任何"学会了抢点"的训练结果都只能是 `--scoring platform` 口径下的、
建立在占位值上的假象。

#### 4.1.3 三顶分值实测后的重跑（2026-10-15 第三轮，`scoring_version=3`）

2026-10-15 晚用探针把**夺控分（主要 80 / 次要 50 一次性）**、**歼煍分
（`Σ(损失×score)`）**与**夺控边界（失守扣分 / 重夺加分）**全部实测出来，
`PENDING_RULES` 清空 ⇒ `verified` 现在含**三个分项**（不再是只有 `remaining`）。

同参数重跑（`--move-radius 4 --episodes 60 --max-seconds 1200 --max-steps 600 --seed 0
--eval-seeds 1000000 1000001 --scoring verified`）→ **86.4 s**：

| 指标 | 4.1.2（只算兵力分） | **4.1.3（三项全算）** |
|---|---|---|
| 恰好停在开局 `234:354` 的局数 | **44 / 60** | **29 / 60** |
| 比分发生变化的局数 | 16 / 60 | **31 / 60** |
| 不同比分组合数 | 9 | **14** |
| 胜负 | RED 60 / BLUE 0 | RED 60 / BLUE 0 |
| 分差（BLUE−RED） | — | 均 −103.2（min −200 / max −40） |

★ **关键变化：出现了 `314:354`（×6）** —— 开局 234 + **80** 正好等于 314，
而 80 就是实测的「主要」夺控点分值 ⇒ **BLUE 在这 6 局里真的拿下了主要夺控点**。
这是 §4.1.2 “策略不再抢点”的反面：**夺控分一旦进奖励，抢点行为立刻出现**。
（另：`254:334`、`274:314`、`231:357` 等都是歼煍分造成的双向变化。）

> 依然**不能拿胜负当战绩**：开局 354:234 的 120 分差远超一局能打出的变化量，
> 所以 RED 60:0 是席位决定的，不是策略决定的。真正可读的信号是**比分是否离开开局值**。

#### 4.1.4 `SCORING_VERSION 6` + **开局快照对齐**后的重跑（当前权威基线）

这一轮又改了两处**会影响奖励**的地方（都有实测支撑）：

也就是说，**奖励一旦与平台一致，MC 就能稳定地抢点**（上一轮 44/60 局零变化）。

> 仍然不能拿胜负当战绩：开局 RED 领先 120 分，一局打不回来；可读的信号是

#### 4.2.5 1 Hz 实时接口接进训练器（2026-10-17）

§4.2.4 的两代都跑在 **回合制** `TwoPlayerEpisode` 上：一次 `step` 是一方一条指令，
**时钟按这条指令自己的时长整段跳** ⇒ 一条 60 秒的机动期间对手**一个决策点都没有**
（这正是 D5 记的缺陷）。1 Hz 的 `RealtimeEpisode` 虽然早就写好（每秒双方各一次、
机动登记为路径并按秒并行推进、`keep`/`stop` 分开），**但训练器一直用的还是回合制**。
本轮把训练器接上：

* `env/neural_train.py` 新增 `interface="serial"|"realtime"`（默认仍 `serial`，不破坏
  既有基线），检查点记录 `interface`，续训不一致直接拒；
* 实时接口下学习目标改成 $R = S_{\text{终}} - S_{\text{开局}}$（席位常数不再直接进优势）；
* 配置：`train/configs/ppo_realtime.json`；命令：
  `py -3.13 run_train.py train --algo ppo --config configs/ppo_realtime.json`；
* ★ 顺手修掉实时枚举的一个**真 bug**：`RealtimeEpisode._enumerate` 把“可见敌人”重建为
  只含 8 个公共字段的 `Unit`，**丢了 `hide`/`ste`/`e2`** ⇒ 投影里 `observe_range`
  不减半、`unit_height` 也错，于是枚举会 advertise 出执行时被 `can_observe` 拒的
  攻击（随机策略一撞就报“射击失败：不可观察”）。现在可见敌人直接用权威对象，
  迷雾照旧（只放本 tick 可见的敌人）。

成本实测（真实地图、半径 3、候选均值 ~500）：**一次决策 ≈ 22 ms**（策略前向+特征）+ 环境 6 ms
⇒ **单局（1200 次决策）≈ 107 s 墙钟**，比回合制（~2.1 s/局）慢 ~50×——慢的是**决策点数量**
（1200 vs ~12），不是单步成本。已做两处安全优化（两处都是**纯函数记忆化**，不动物理数值）：
特征哈希 `_emit_cache` + 几何 `lru_cache`（`split_mapid`/`make_mapid`/`neighbors`/`to_cube`）
⇒ **106.7 → 86.2 s/局**；cProfile 显示剩下的热点在**候选枚举**（`legal_actions` 约占 1/3，
单局 `_validate` ~8 万次、`neighbors` ~22 万次）。所以首炉只跑 12 局专门打通管线；
要大样本必须先降“每次决策”成本（见 `docs/训练困难清单.md` E7）。

**首炉结果（12 局，2026-10-17）**：`interface=realtime`、`max_seconds=1200`、半径 3、`batch_episodes=4`。
每局**正好 1200 次决策**（⇒ 1 Hz 语义到位，不再是回合制的 ~12 次）。用时 2027.6 s
（同时段并行跑了别的测量，偏慢；无干扰时 86 s/局 ⇒ 12 局约 17 min）。

#### 4.2.6 并行 rollout + 更新侧瘦身（2026-10-17）

⚠️ **本节的绝对秒数偏慢**：这台机器电源方案是 `SILENT`，实测 CPU 只跑到标称频率的
**63%**（`\Processor Information(_Total)\% Processor Performance`），同一配置在不同时段
能差 2.4 倍。所以**只比同一时段内的相对值**，别拿这里的秒数当硬件基准。

**为什么动这里**：1 Hz 语义下一局 1200 次决策、每方每秒都要决策，单局 100–120 s 墙钟；
可这一局只用到一个核（14 核 20 线程的机器上纯浪费）。同时剖析发现成本结构已经变了：

| 阶段（单局 1200 决策） | 串行 | 说明 |
|---|---|---|
| rollout（策略前向 + 特征 + 环境枚举） | ≈ 72 s | 真正"每决策"的部分 |
| `update_batch`（PPO，4 epoch） | ≈ 46 s | 逐决策 × epoch，纯串行 |
| 合计 | ≈ 118 s | |

**做法**

1. **批内并行 rollout**：`NeuralTrainer(rollout_workers=N)`。抽出一个可 pickle 的
   `_RolloutRunner`（只含 snapshot / manifest / interface / episode_config /
   observation_schema / seed / entropy_every / allow_real / policy_seed_mode 这 9 个
   **不可变**属性），`NeuralTrainer._rollout` 只是**委托**它 —— 所以串行路径的代码一字未改，
   子进程跑的是同一份实现（不留两份会漂移的副本）。
2. **采样流口径** `policy_seed_mode`（`env.neural_train.POLICY_SEED_MODES`）：
   - `shared`（历史默认）：所有局沿用**同一条** `policy.rng` ⇒ 第 k 局用到的随机数取决于
     前面跑过多少局，**不可并行**；
   - `per_episode`：每局按 `derived_seed(seed, 局种子, 席位, "policy_sample")` 独立播种
     ⇒ 局与局无关、顺序无关、**可复现**，所以能并行。
   `rollout_workers>1` 时强制 `per_episode`（否则并行度会改变结果）。
   具体实现是给 `NeuralPolicy.sample()` 加一个可选 `rng=` 参数，per_episode 走**局部流**，
   **不碰策略自身的 `rng`** ⇒ 串行与并行的检查点除 `rollout_workers` 外逐字节相同
   （第一版让 per_episode 直接改写 `policy.rng`，检查点就差了 —— 这是个真坑）。
3. **只并行同一批**：批内策略是冻结的，所以"更新发生在第几局之后"与串行完全一致，
   并行度不影响优化序列。
4. ★ **Windows 用 spawn**：调用方脚本必须有 `if __name__ == "__main__"` 保护，否则子进程
   重新导入主模块会把整个脚本再跑一遍（表现为 `BrokenProcessPool`）。

**等价性证据**：`tests/test_neural_train_parallel.py`（8 项）。核心一条：
同一配置下 `rollout_workers=1, policy_seed_mode="per_episode"` 与 `rollout_workers=2`
的 **record 逐字段相同**、`episodes_attempted/completed`、`updates`、`pending` 相同、
检查点（去掉 `rollout_workers` 元数据）**逐字节相同**；`evaluate()` 的报告除
`elapsed_seconds` 外完全相同（评测本来与顺序无关：动作由派生的 `eval_rng` 抽、策略冻结）。

**实测（同一时段内）**

| 场景 | 串行 | 4 进程 | 加速 |
|---|---|---|---|
| 4 局 rollout（1200 秒局，单局 67–79 s） | 291 s | **93.4 s** | **3.1×** |
| 4 局 rollout（300 秒局，单局 12–16 s） | 60 s | **19.9 s** | **3.0×** |
| 单局成本（1200 决策）= rollout/N + update | 72 + 46 = 118 s | 18 + 46 = **64 s** | 1.85× |

⇒ **瓶颈已经从 rollout 转移到 `update_batch`**：再往上堆进程数，边际收益会很快变零。

**更新侧的两处提速**（都保持"按样本顺序累加"，数值**逐字节不变**）

| 改动 | 前 | 后 | 依据 |
|---|---|---|---|
| 动作梯度散加：`np.add.at` 从**每个候选一次**合并为**每个决策一次** | 18.7 万次/批 | 1600 次/批 | `ufunc.at` 对重复下标**按出现顺序**累加，拼接保持了「候选序 × 候选内特征序」⇒ 累加序列逐项不变 |
| `_loss_gradients` **分块**（`GRADIENT_CHUNK = 64`） | 一次性为整批建 `forward` | 每块 64 条 | 每个 forward ≈ 1 MB（`joint` = 候选数×3h 的 float64）⇒ batch 4 × 1200 决策要 **4.8 GB**，实测表现为"父进程 7.5 GB、CPU 停滞几分钟"的假死；分块后峰值 RSS 降到 ~2 GB |
| `update_batch` 墙钟（2 局 × 200 决策 × 4 epoch） | **20.8 s** | **7.46 s** | 两项合计 2.8× |

两道护栏都过了：`tests/test_neural_ppo.py::test_default_checkpoint_bytes_and_arithmetic_unchanged`
（对着测试文件里**独立保留的 PPO 之前那版实现**逐字节比检查点）。另外新增
`NeuralPolicy._value()`（只算观察投影 + 值头，与 `_forward(...)[4]` 同一条表达式），
给"必须先拿到全部 value 才能算优势"的老口径用，PPO 走冻结的 `advantages` 时不会调用。

**下一步的余量（E7 未清部分）**：`update_batch` 仍占单局 40–70%。可动的只剩
①改算法口径（`update_epochs`、对决策做子采样）②把梯度也并行（会改变加法次序，
与本仓"默认算术逐字节可比"的护栏冲突，需要先定口径）。

★ **batch 别放大**：同是 1200 秒局，`update_batch` 的墙钟随 batch **超线性**上升 ——
实测 4 局 **162 s**（40 s/局）而 6 局 **537 s**（90 s/局）。先怀疑是 Python 循环 GC 在
几百万个小 numpy 对象上来回扫，做了对照实验：更新期间 `gc.disable()` 只快 **1.06×**
（162.2 → 153.0 s）且检查点逐字节相同 ⇒ **不是 GC 的锅**，更像大堆分配器碎片 + 长时间
满载后的降频复合效应。结论：**batch 保持在 4 左右**，靠并行度拿吞吐，不要靠堆 batch。

★★ **同一进程里连续做更新会明显退化**：8 局 / batch 4 的端到端试跑里，第 1 次
`update_batch` ≈ **165 s**、第 2 次（同样 4 局、同样配置）已经 **> 450 s** 还没结束，
而 4 个 worker 早已空闲（rollout 只占 ~90 s）。⇒ **单进程别塞太多批**：
要么小 `episodes` 多次调用 + 检查点续跑（`checkpoint`/`resume` 本身就是为"分批不改变优化"
设计的），要么一批一个进程。这条也是"为什么这轮没交出更大样本的并行基线"的直接原因。

> ⚠️ **后续更正**：上面的"退化"后来被证伪了大半 —— 同一进程里**背靠背**两次更新实测
> 是 **162 s / 153 s**（见 `docs/训练困难清单.md` E7 的 GC 对照实验），没有退化。
> 那次 450 s 更像**长时间满载后的降频**（本机电源 SILENT）。所以分段跑的价值主要是
> **每段落一次检查点、失败不白跑**，而不是"规避同进程退化"。

### 4.2.7 长跑怎么跟读进度（2026-10-17）

长跑（几十小时级别）最怕"只看得到结束时间"。所以加了两个东西，都是**纯外挂观测**：

| 组件 | 作用 |
|---|---|
| `NeuralTrainer(progress_path=...)` / CLI `--progress` / 配置键 `progress` | 每完成一局**追加一行 JSONL**：`wall / attempted / completed / updates / seed / side / own / R / diff / result / decisions / episode_seconds` |
| `tools/monitor_train.py --progress <jsonl> --total N [--follow --interval 20]` | 打印 `已完成/总数、局/min、ETA、更新次数、近 N 局的平均 R 与胜平负、单局秒数、台账距今多久` |

```powershell
py -3.13 tools/monitor_train.py --progress train\analysis\longrun\progress.jsonl --total 1000 --follow
# 4/1000 局 (0.4%) | 1.71 局/min | ETA 9.7 h | 更新 1 次 | 近 4 局 R=28.25 分差胜/平/负=2/0/2 单局 61 s
```

三个必须成立的性质（`tests/test_neural_train_progress.py`，5 项）：
① 开台账与不开台账，**训练记录与检查点逐字节相同**（台账只写文件，不碰学习）；
② 每局一行、`attempted` 单调、`completed ≤ attempted`、每 `batch_episodes` 局 `updates` +1；
③ 台账**写不了就自动关掉**（不拖累训练）；④ 监控摘要是纯函数（速率/ETA 可单测）。

分段长跑的做法（每段独立检查点 + 报告，台账跨段续写，`attempted` 一路递增）：

```powershell
foreach ($i in 1..5) {
  py -3.13 run_train.py train --algo ppo --config "configs/_longrun_$i.json"
  if ($LASTEXITCODE -ne 0) { break }
}
```

#### 4.2.8 纯冗余消除：**−29%**（2026-10-17，轨迹逐字节不变）

基准方法（受训练进程干扰，所以只认 **CPU 时间**，各跑 4 次取最小）：
**39.8 → 28.2 ms/决策（−29%，1.41×）**。

**行为不变的证据**：固定策略 + 固定种子的"黄金轨迹指纹"——动作序列、候选数、观测特征
数组字节、终局分的 sha256 **前后完全相同**（`f3332f50…`）；`hex_env_diff --radius 3` 0 分歧。

| 改动 | 为什么原来浪费 |
|---|---|
| `Game.stack_index()` + `step_seconds(..., stack=)` | 堆叠检查每次**扫全部 36 个单位**，而一次 `legal_actions` 要调 600+ 次 `step_seconds`。索引由调用方**一次成型后传入**（不缓存在 Game 上）⇒ 不存在"缓存陈旧"风险 |
| `_features` 的路径键改用不可变元组增量拼接 | `emit` 原来对**每个叶子**都做一次 `tuple(map(tuple, path))`（每次决策 ~1 万次）⇒ `emit` 自身耗时 −54%，`_features` 累计 −24% |
| 射击候选把 `can_observe` 移出武器循环 | 可观察性只取决于**一对单位**，却写在 `for wid in u.wz` 里，每对重复 2–4 次 |
| 集火射击先建"每格代表敌人"表 | 原来在 (格 × 己方单位) 二重循环里跑 `next(...)` 扫全部单位 |

★ **一个失败的假设**：我原以为 `can_observe` 的主消费方是射击循环，实测每决策仍有 1275 次 ——
真正的消费方是**观测构建**（`observe()` 与 `_remember()` 各做一遍 O(单位²) 通视扫描，每 tick 4 遍）。
这块**还没动**，是下一步最大的一块（约占 14%）。

★ **两个操作教训**（都写进了仓库记忆）：① 长跑不能挂在编辑器终端里（被清理时子进程连坐，
已白跑 96 局）；② **训练跑着的时候不要 `build_train_env.py` 同步 `train/`** ——
新段启动瞬间可能读到写了一半的文件，也可能让新段与旧段用不同代码。

**第二块：每 tick 的可见性快照（再 −13%，累计 −38%）**

还剩下最大的一块是**观测构建**：`observe()` 与 `_remember()` 各自跑一遍 O(单位²) 通视，
每个 tick 同一批对要算 **4 遍**。做法：`HexwarEnv` 上带一张 `(观察者, 目标) → bool` 的快照，
配一个**状态指纹**（`second` + 每个单位的 `pos/blood/ste/color/alt/carrier/hidden/out_of_control`），
指纹一变就整张丢掉。

⚠️ **踩到的坑（值得单独立一条）**：测试会用 `patch.object(game, 'can_observe', ...)`
把方法**替换**掉——这时状态指纹不变、但**实现**变了，缓存会拿旧实现算出的 True。
修法：`"can_observe" in game.__dict__` 时（被 patch 过）**完全关掉缓存**。
`Game` 没有 `__slots__`，所以这个判据既便宜又准确。
这条由 `tests/test_step_cost_equivalence.py` 的 3 项锁住（快照 vs 直接调用逐对一致、
状态一变即失效、被 patch 时完全不走缓存）。

#### 4.2.9 学习目标换成「净胜分增量」（2026-10-17，目标从"能训"转到"练强"）

**旧口径的致命缺陷**：`R = 本方终局分 − 本方开局分`。平台三项分值里，
「夺控分」是**按旗子归属给分**的：敌方拿下主要点，敌方 +80，**本方分一分不掉**。
所以旧奖励对"丢点"**完全无感** —— 策略最优解退化成"我涨分就行，随便他占"，
这解释了为什么 $R$ 能长期为正而胜负仍是席位决定。

**新口径**（`REWARD_MODES = ("net_gain", "own_gain")`，默认 `net_gain`）：

$$R = (S^{\text{本}}_{\text{终}} - S^{\text{本}}_{\text{开局}}) - (S^{\text{敌}}_{\text{终}} - S^{\text{敌}}_{\text{开局}}) = \Delta\text{净胜分}$$

它与平台判胜负的**净胜分**同向；开局席位常数（蓝 234 / 红 354）被两边各扣一次后
**完全抵消**；敌方涨分 → 奖励变负 ⇒ 策略才学得到"别丢点"。
记录里同时保留 `own_gain` / `net_gain` 两个量，进度台账也各写一列，便于对照。

> ⚠️ `net_gain` 需要接口给出**双方**开局分（`opening_scores`）。1 Hz 实时接口有；
> 回合制 `TwoPlayerEpisode` 没有，会自动退回历史口径（终局本方分）。检查点绑定
> `reward_mode` / `trajectory_stride`，换了就拒绝续跑（不是同一条学习目标）。

**配套：轨迹子采样 `trajectory_stride`**（默认 1，本轮用 4）。
终极奖励是**每局一个标量**，同一局里所有决策共享它 —— 所以按步长抽稀只减少"同一信号的
重复样本"，不改变局级学习目标，却把 `update_batch` 成本与检查点体积都降到 1/k
（一局轨迹的 JSON 原本约 **200 MB**，这也是 `ckpt_seg_01.json` 涨到 440 MB 的原因）。

`copy.deepcopy` 整个环境，而环境里带着**整张真实地图（2721 格）**。已改为与

### 4.4 局限（不夸大）

1. **一局只有 ~11–14 次决策**。真实地图上机动的游戏时间很贵（一格 6–60 秒），
   1200 秒时钟只够每方做十来次决策 ⇒ 一局能提供的训练样本极少。
   想扩大样本只能：加长 `--max-seconds`（如 3600）、或堆局数。
2. **查表法在真实地图上几乎必然稀疏**：60 局也只覆盖约 600 个状态，
   而观察空间是"地图 × 兵力 × 迷雾"的组合。
3. **奖励是纯终局分差**（中途恒为 0），而终局分差又被初始分差主导
   （开局 **234 vs 354**）⇒ 学习信号弱，160 局 PPO 未能超过初始策略。
   而且默认口径（`verified`）**把未确证的夺控分排除掉了** ⇒ 抢点在奖励里没有价值，
   唯一可学的只剩消耗战（见 §4.1.2）。要能练"抢点"，必须先把夺控分口径问清楚。
4. **实现在快速口径上加了一条手册规则**（冲锋只能走 1 格），
   并用差分用例 + 真实地图差分工具守住等价性；但这仍是"两个口径互证"，
   不是"与服务端逐位一致"。
5. **本次只解决"能不能练"，没解决"练了有没有用"**。下一步该动的是奖励/课程设计，
   而不是继续堆局数。
