## 1. 已实测的事实

### 1.1 平台计分页结构（`Report_All.asp`）

页面只给出**分项名**与数值，不给分值或公式：

```
红方夺控点得分        / 蓝方夺控点得分
红方剩余兵力 得分     / 蓝方剩余兵力得分
红方歼灭对手兵力得分  / 蓝方歼灭对手兵力得分
（红方摧毁重要目标得分 / 蓝方摧毁重要目标得分）   ← 整行被 HTML 注释掉
红方胜分             / 蓝方胜分
```

- 数值格形如 `<td><em class="RED">354分</em></td>`；**每个分项头在同一行出现两次**，
  所以解析必须 `split(表头, 1)`（踩过这个坑：`split()[1]` 只会取到两个表头之间的 26 个字符）。
- 开头是玩家名（例：`USER_B`），不是阵营名；阵营由 `class="RED"/"BLUE"` 区分。
- 想定 7527 有 3 个夺控点（`City_Get.asp`）：`主要` ×1、`次要` ×2。

### 1.2 开局基准值（413 次抓取完全一致）

| 分项 | 红 | 蓝 |
|---|---|---|
| 夺控点得分 | 0 | 0 |
| 剩余兵力得分 | **354** | **234** |
| 歼灭对手兵力得分 | 0 | 0 |

> 之所以长期以为"夺控分/歼灭分反推不出来"：早期 33 个采集文件全在**开局态**，
> 没有一次是在占点或掉血之后取的。要用探针**主动去占、主动去打**才能读到跳变。

### 1.3 单位的分值就是 `score` 字段（= `Obj_Get` 下发的 `score`）

想定里 36 条单位的 `score` 与装备表权重一致，例：
`中型坦克 10`、`坦克 10`、`装甲车 10`、`步兵班 382 → 3`、`步兵班 392 → 4`、
`无人察打车 5`、`旋翼无人机 2`、`巡飞弹 0`、`掩体 0`。

### 1.4 实测方法（探针）

`tools/hex_score_probe.py`：以 1 Hz 采样 `Report_All.asp`，**每次页面一变就记一条 tick**。

- `--phase capture`：把一支部队机动到某个夺控点格上（`Obj_104442` 那套 `ComPost` 流程），
  占下后继续采样 60 s 看是否随时间增长；
- `--phase kill`：挑一对"能真打出伤害"的交战方（按**预期攻击级别**筛选，`预期攻级=None`
  的武器打了也白打——防空导弹打坦克就是这样，实测 14 发全空），逼近到 1 格后连续开火，
  每掉 1 兵力就采一次页面。

### 1.5 ⚠️ 一个必须记住的坑：武器 / 目标类型路由

第一次歼灭探针（`score_probe_kill_20261015-220008`）给坦克配了**防空导弹**，
14 发全部返回空串、目标血量不动，页面 30 个 tick 里**一次都没变**。
换成**重型坦克炮打坦克**（预期攻级 = 10）立刻命中。所以：
**计分不能只看"有没有开火"，要看"预期攻级是否为 None"**。

## 2. 剩余兵力分（已对账）

$$\text{剩余兵力分} = \sum_{\text{已上阵单位}} \text{score}\times\text{blood} \;+\; \sum_{\text{车内载员}} \text{score}\times\text{编制兵力}$$

**两组数字同时精确命中**：

| 阵营 | 上阵 Σ(score×blood) | 车内载员 Σ(score×编制) | 合计 | 平台 |
|---|---|---|---|---|
| 蓝 | 207 | 3 × 步兵班(3×**3**) = 27 | **234** | **234** ✅ |
| 红 | 240 | 3 × [步兵班(4×**4**) + 无人察打车(5×**4**) + 旋翼无人机(2×**1**)] = 114 | **354** | **354** ✅ |

对照（其它口径都对不上）：

| 口径 | 红 | 蓝 | 与平台差 |
|---|---|---|---|
| Σscore（**仓库现状**） | 60 | 75 | −294 / −159 |
| Σ(score×blood) | 240 | 207 | −114 / −27 |
| Σ(score×(blood+sons)) | 360 | 237 | +6 / +3 |
| **上阵 Σ(score×blood) + 载员 Σ(score×编制)** | **354** | **234** | **0 / 0** ✅ |

**编制兵力从哪来**：想定里 15 条载员条目 `blood=0`（人在车内），编制不可读；
但**下车会在服务端新建实体**，其 `blood` 就是编制兵力 —— 由此得到
`步兵班 382 → 3`、`步兵班 392 → 4`、`无人察打车 → 4`（各有下车采集实证）；
`旋翼无人机 → 1` 是**由平台分项反解**出来的（未直接观测到下车样本）；
`巡飞弹 score=0`，恒不影响。

### 2.1 引擎实现

- 实现位置：**`engine/scoring.py`**（`side_score` / `breakdown` / `CARRIED_ESTABLISHMENT`）；
  `env/hexwar_env.py::score()` 直接调它。
- 编制兵力表：`CARRIED_ESTABLISHMENT = {382: 3, 392: 4, 397: 4, 394: 1, 389: 0}`。
- **落地口径下引擎输出 = 平台数值**（红 354 / 蓝 234），该对账是
  `tools/hex_score_audit.py` 的一个**断言**（不一致就 `exit 1`），不是人工核对。
- 副效应（已知且刻意）：敌我单位血量会以「剩余兵力分合计」形式被双方看到，
  这与平台计分页一致；相应地，奖励的基准差是 **234:354**。

### 2.2 奖励隔离：未实测的分项永远不进训练

`score()` 同时给出两个总分，**用哪个由调用方显式选择**：

| 键 | 含义 | 用在哪儿 |
|---|---|---|
| `total` | 三个分项**全算**（平台式） | 对账 / 展示 |
| `verified` | **只算已实测分项**（现 = `remaining + killed + captured`） | **默认奖励口径**（`scoring_mode="verified"`） |
| `unverified` | 本次算分依赖了哪条**未实测前提 / 没说清的数据** | 告警；调用方自己判断 |
| `pending_rules` | 仍未实测的**规则** —— **现为空 tuple**（夺控边界已实测） | 版本化说明 |

- 默认口径是 `verified`：`HexwarEnv` / `TwoPlayerEpisode` / MC / PPO / `policy_eval`
  全部默认只用已实测部分当奖励；
- 需要平台式总分时显式 `--scoring platform`（或 `scoring_mode="platform"`），
  该选择会写进检查点与报告；
- **现在两者相等**（三项都实测了），但这套隔离保留着：只要将来出现新的未确证项，
  它会自动不进奖励，而不是悄悄污染。

⚠️ **平台式 `diff` 里同一份损失会算两遍**，这**已经实测确认是平台行为**，不是我们的 bug：
输方 `remaining` 减 X、赢方 `killed` 加 X，于是 `diff` 变化 2X（见 §4 的实测数字）。
`verified` 口径下同样如此（因为 `killed` 现在是已实测分项）。

### 2.3 载员归属：用载具 ID，不用格号

快照里的 15 条载员记录只有 `pos2`（当时的载具格），而 `pos2` 是"目标格/旧格"：
**载具一机动就不再指向它**。靠 `pos2` 现场匹配的后果是：载具离开原格后载员分值
凭空消失，等价于"惩罚机动"。

现在载入时（`Game.link_carried`）就按证据强弱固化关系：

1. 载具 `son` 图标串含该载员的 `ico`（**一位一用**，避免同型号载员重复占位）；
2. 该格唯一的车辆/飞行器（`typeid` 2/3）；
3. 该格唯一的单位。

实测 7527 开局 15 条载员**全部靠第 1 条唯一匹配**（例：M113TW 的 `son` 含 `COD-M4`；
ZBD100 的 `son` 含 `PLA2-191` / `UGVS` / `YY4` / `WS43`）。
定不下来的不会静默处理：`carried_ambiguous` / `carried_unlinked` 会进入 `unverified`；
**未知型号的载员编制返回 `None` 而不是 0**（0 会静默少算，`None` 会进 `unverified`）。
另外**下车**时会把阵营色与编制兵力恢复（平台下车就是新建一个带阵营、`blood`=编制的实体），
否则那个单位会一直"像载员"而不进剩余兵力分。

### 2.4 检查点绑定计分版本

换公式以后，同一快照下的旧检查点（以及它未完成的批次）如果还能载入，
就会把"旧口径学到的值"当成"新口径的初始值"继续训练。所以：

- `engine/scoring.py::SCORING_VERSION` 是口径版本号，任何改变分值语义的改动都必须 +1；
- MC / 神经网络检查点写入 `scoring_version` 与 `scoring_mode`；
- 载入/续跑时两者逐步比对，不一致就**报错拒绝**；
- **老检查点**（根本没有这两个字段）同样拒绝，而不是默认按新口径解释。

## 3. ★ 夺控分：实测 主要 = 80，次要 = 50，**一次性**

| 实测 | 动作 | 平台夺控分变化 | 证据目录 |
|---|---|---|---|
| ① | 蓝方占下 **主要**点（`RoomSecond=2` 时） | 蓝 0 → **80**，此后 60 s 不再增长 | `score_probe_capture_20261015-215720` |
| ② | 蓝方占下 **次要**点（`RoomSecond=3` 时） | 蓝 0 → **50**，此后 60 s 不再增长 | `score_probe_capture_20261015-215820` |

原始 tick（②）：

```
- tick 0   21:58:24 RoomSecond=0   夺控 红0/蓝0   兵力 红354/蓝234  歼灭 红0/蓝0
- tick 3   21:58:27 RoomSecond=3   夺控 红0/蓝50  兵力 红354/蓝234  歼灭 红0/蓝0
```

结论与实现：

- **不是**"每秒加分"、**不是**"按比例"：占下的一瞬间就加满，之后恒定 ⇒ **一次性**；
- `主要`(80) ≠ `次要`(50) ⇒ 两个名称必须分开建表，不能共用一个数；
- 实现：`CAPTURE_POINT_SCORE = {"主要": 80, "次要": 50}`，
  未知名称返回 **`None`** 并记 `capture_point_name_unknown`（**不猜、不按 0 静默处理**）；
- ⚠️ **旧值是错的**：代码里曾写死的 `CAPTURE_POINT_SCORE_PLACEHOLDER = 10`
  **没有任何依据**（手册没写、实测恒为 0），与实测差 **5~8 倍**。
  任何基于"10 分/点"的净胜分、胜率或训练曲线**全部作废**。

### 4.2 ★★ 专项实验：乘员在/**不在**车里，车被歼时分怎么算

这一条前后测了两次：第一次**没注意到平台开局乘员根本不在车里**而得出错误结论，
第二次把乘员真装进车里才拿到真值。两个情形的结论**相反**，必须分开记。

#### 情形 A：平台开局——乘员与载具**同格、各自是独立单位**

对象：红方 **ZBD100 火力支援车**（`score=10` / `blood=4`）。它那一格上还**同格站着** 4 个红方单位
（步兵班 392 `score=4`、无人察打车 397 `score=5`、旋翼无人机 394 `score=2`、巡飞弹 389 `score=0`，
共 38 分）——**它们不在车里**。

蓝方 T80B 用重型坦克炮把它打到 0 血（`--target-ico ZBD100`，
证据 `score_probe_kill_20261015-222414`）：

| tick | 事件 | 剩余兵力 红/蓝 | 歼灭 红/蓝 |
|---|---|---|---|
| 0 | 开局 | **354**/234 | 0/0 |
| 39 | 车体掉 1 血 | **344**/234 | 0/**10** |
| 40 | 车体掉 1 血 | **334**/234 | 0/**20** |
| 41 | 车体被歼（2→0） | **314**/234 | 0/**40** |

**只变化 40 = 车体 `score 10 × 4 血`**。同格的 4 个乘员（共 38 分）**分文未动**——
因为它们是**独立单位**，车毁根本没碰到它们（也解释了为何 354 = 240 + 114 仍成立）。

#### 情形 B：真用 `ObjInto` 装进车里——乘员**随车被歼**

探针 `tools/hex_load_kill_probe.py`：先把红方步兵班（392，`score 4`、编制 4）装进同格的
ZBD100（确认它变成 `pos=0 / blood=0 / color=''`，且**计分页不变**），再让蓝方坦克把它打到 0 血
（证据 `loadkill_20261015-223027`）：

| tick | 事件 | 剩余兵力 红/蓝 | 歼煍 红/蓝 |
|---|---|---|---|
| 0 | 开局（乘员仍在格上） | **354**/234 | 0/0 |
| 43 | 载具被歼 | **298**/234 | 0/**56** |

`354 − 40（车体 10×4）− 16（乘员 4×4）= 298`，对手歼煍 +**56**。

⇒ 三条结论：

1. **真在车内**的乘员**随车被歼**：其 `score × 编制` 从剩余兵力分里扣除，
   并**一并记给对手的歼煍分**（= 我们的 `killed`）；
2. 车死后乘员记录**仍在**（`pos=0/blood=0/color=''`），但 `Obj2_Out` 返回 **`0`**
   ⇒ **放不出来**，“记录还在 ≠ 人还活着”；
3. **上车/下车不改变计分页**（装进去那一刻分值不变，因为平台按**编制**折算）。

⚠️ **曾经把情形 A 当成“载员分永不随车消失”并据此改了一版（v4）——那是错的**，
因为情形 A 里乘员压根儿不在车里。**v5 已回退成正确口径**：
`remaining` 只在**载具存活**时把车内载员按编制计入；
`killed` 在**载具被歼**时把载员编制一并计入（同时把载员从 remaining 里扣掉）。

> 教训：**先确认“对象到底处于什么状态”再下结论**。同一个“打掉载具”动作，
> 在“同格部署”与“真在车内”两种状态下结论**完全相反**——
> 这也是 `snapshot/parsed` 那一版“乘员在车内”的快照与平台开局不一致造成的坑（见 §8）。

> 顺带解释了为何此时才能发现：之前 60 局 MC 里 **44 局双方零损失**，
> 而这个 bug 只在“**载具被打掉**”时才会发作。
> 另外，实时流（`ObjAjax`）**不下发车内记录**（本次 54 tick 采样里车内记录数恒为 0），
> 所以只能靠**计分页的跳变量**反推，不能靠单位列表。

由此**逐条排除**了原先的假设与备选口径：

| 备选口径 | 是否成立 | 判据 |
|---|---|---|
| **按损失兵力逐点计**（`score × 损失兵力`） | ✅ **成立** | 掉 1 血 → ±10；掉 2 → ±20；总计损失 4 血 → 40 = 4×10 |
| 只有"整单位被歼"才计分 | ❌ 排除 | 掉第 1 血时歼灭分已经 +10 |
| 载员是否与载具重复计算 | ❌ 排除（两种情形都测过） | 情形 A：同格乘员分文未动（只 ±40）；情形 B：车＋车内乘员各算一次（±56） |
| 与剩余兵力分不互补 | ❌ 排除 | 每一行都是"红方 −X / 蓝方 +X"，**逐点互补** |
| 有上限 / 与任务挂钩 | ❌ 未出现 | 4 血损失线性累加到 40，无封顶迹象 |

> 也就是说：**`diff` 里同一份损失变化 2X 是平台口径本身**（输方少算一份、赢方多算一份），
> 不是我们重复计算。`verified`/`total` 两个口径下都如此。

## 5. ⛔ 仍然未确证的两条边界

### 5.1 ✅ 夺控的失守 / 重复夺回：已实测（`captured_defence_rules` 已关闭）

探针 `tools/hex_flip_probe.py` 一次性跑完“占 → 撤远 → 对方夺回”，逐次记录分值：

| tick | 动作 | 归属 | 夺控分 红/蓝 | 兵力分 红/蓝 |
|---|---|---|---|---|
| 0 | 开局 | 均无主 | 0 / 0 | 354 / 234 |
| 4 | 蓝方占下 `次要` | **BLUE** | 0 / **50** | 354 / 234 |
| 6 | 蓝方**撤到 2 格外**（不在本格、也不在 6 邻格） | 仍 **BLUE** | 0 / 50 | 354 / 234 |
| 23 | 红方走上该格并 CityTake | **RED** | **50** / **0** | 354 / 234 |

⇒ 三条结论：

1. **失守方会被扣分**（蓝方从 50 直接归零，而不是“保住已得的分”）；
2. **重夺方按同一分值加分**（红方 +50，不衰减、不封顶）；
3. **撤离不会失去归属**（离开原地不算失守），但**被对方夺走**就会丢分。

所以原先的实现（`engine/scoring.py::_from_parts` = **按“当前归属的夺控点分值”求和**）
**本来就是对的**：不需要改一行代码，现在是“**已实测**”而不是“未确证”。
`PENDING_RULES` 随之清空。

#### 5.1.1 交叉验证了手册 3.13（夺控条件）

## 8. ★★ 顺带修掉一个**训练数据保真**问题：快照不是开局态

做上面那个“装车再打掉”实验时发现的：

- **平台开局**（`RoomStart` 后第一条 `Obj_Get`）：36 个单位**全部在场**，
  乘员与载具**同格**、各自是独立单位，`blood` 就等于编制（实时单位表里没有一条 `pos=0`）。
- **我们的 `snapshot/parsed/units.json`**：15 条乘员被写成 `pos=0 / blood=0 / color=''`
  （那是 HAR 里真人点过“全员上车”之后的状态），而且 `坦克1排` 已经前出到 160062
  （平台开局在 190096）。⇒ 它是个**中局**状态，不是开局。

处理（可复跑）：

```powershell
py -3.13 tools/hex_sync_snapshot_opening.py            # dry-run：列出要改的条目
py -3.13 tools/hex_sync_snapshot_opening.py --apply     # 写入（旧文件备份为 units.har.json）
py -3.13 tools/hex_score_audit.py                       # 断言“引擎 == 平台 354/234”
```

共改 **16 条**：15 条乘员落回载具格（`color` = 载具那方的颜色、`blood` = 编制）、
外加 `坦克1排` 的位置。改完之后：

- 开局**不再有**“车内记录”；
- `hex_score_audit` 依然精确命中 354/234，而且现在是 **`Σ(score×blood)` 自己就能命中**
  （因为乘员已是独立上阵单位）；
- **编制表五型全部变成实测值**（`382→3`、`392→4`、`397→4`、`394→1`、**`389→3`**），
  其中 `389 巡飞弹` 此前误写为 0（它 `score=0`，不影响分值，但影响下车/发射后的兵力）。

> 意义：新的一局从**平台真正的开局**开始，乘员是**暴露在地面上**的（会被火力直接打、
> 也可以主动上车），而不是一开始就躲在车里。旧快照会让智能体漏掉整个“开局暴露期”。

## 9. 训练侧的影响

- **旧结论作废**：此前 60 局 MC 里“44 局双方零损失、策略不抢点”的直接原因是
  **夺控分被当成未确证项排除在奖励外**（占点没有任何奖励）；
- 现在三项都进奖励（夺控 80/50 一次性、歼灭 `Σ(损失×score)`），**抢点行为出现**：
  v6 基线 60 局里 **38/60 局比分离开开局值**，其中 **36 局恰好 `284:354`**
  = 234 + **50**（拿下 1 个「次要」点）；另有 1 局 `364:354`（+130 = 80+50）。
- 但 **PPO 160 局仍未出现可测量的提升**（8 局评估里初始与训练后完全一致）。
  所以**“奖励不完整/不正确”已不是瓶颈**，剩下的是样本量（一局 ~12 次决策）
  与“胜负由席位决定”（开局 354:234）。见 `docs/真实地图训练.md` §4.1.4/§4.2.3。
